# ADR-002: Serve the subscription dashboard and API from the same Cloudflare Worker

**Date:** 2026-11-12  
**Status:** Accepted and deployed; user-verified with fictional demo data

## Context

The transferred HW5 dashboard originally ran through VS Code Live Server on Codespaces port 5500, while its API ran through a Cloudflare Worker on forwarded port 8787. The browser repeatedly reported "Could not reach the server." The local API passed seven integration tests, so the transport/browser-origin configuration was the plausible problem. Adding the Codespaces origin to CORS alone did not fix it; forwarded ports can require independent Codespaces browser authentication.

## Options considered

| Option | Benefit | Cost/risk |
|---|---|---|
| Keep separate 5500 and 8787 previews | Familiar development flow | Cross-origin requests and forwarded-port authorization failures |
| Point site directly at old HW5 deployed Worker | Easy to load remote API | Relies on historical backend; does not demonstrate newly deployed final project |
| Serve static dashboard as Wrangler Worker assets and call the API on the same origin | One public URL, avoids cross-port authorization and CORS issues | Requires `public/` asset copies and Wrangler `[assets]` configuration |

## Decision

Use the third option. `wrangler.toml` sets `[assets] directory = "./public"`, with `public/index.html`, `public/styles.css`, and `public/app.js`. The frontend recognizes the Worker origin and calls `/entries` on the same host; `worker.js` continues to implement the API with an existing D1 binding. The default Worker deployment URL is:

https://mgt3745-final-subscriptions.mgt3745-hw4-giancarlo.workers.dev/

## Verification and implications

Wrangler deployed the Worker and all three assets. A direct remote D1 query showed the `entries` table existed. The user confirmed live browser operations: save a fictional subscription, refresh and observe it still present, delete the entry, and observe the monthly total update. The local API tests passed 7/7.

**Security limitation:** same-origin hosting solves browser connectivity, **not** access control. The API is unauthenticated with shared records; fictional demo data only. A future real-user product requires authentication, per-user data isolation, and review of access controls. The local D1 export was tested as an exit step, but remote export/restore was not tested.
